# Native SwiftUI with `MenuBarExtra`, built as a pure SwiftPM package

The app is built in Swift 6 with SwiftUI. The menu bar is handled by `MenuBarExtra` in `.window` style; the project is a pure SwiftPM package without an `.xcodeproj` and without third-party dependencies; the minimum version is macOS 27. The deciding factor is that agents build the app alone and verify it themselves: build, tests and PNG snapshots run entirely via `swift build`/`swift test` without the Xcode GUI (verified locally), the strict compiler catches errors early, and the tricky part of a menu bar app (status item, launch at login, no Dock icon) comes from Apple APIs instead of plugins. On top of that, at 16 MB of RAM when idle the stack is the lightest, in line with the guiding principle "simple".

## Considered Options

- **Tauri 2:** a web UI that agents can conveniently check in a browser. In exchange: two toolchains (Rust and Node), about three times the memory, panel positioning and launch at login (without SMAppService) only via plugins, and the click bug in the macOS 27 menu bar was open until September 2026.
- **Electron:** the largest ecosystem, but a package of about 300 MB, 80 MB of RAM, 4 processes, a major version every 8 weeks, and open macOS 27 issues.
- **AppKit `NSStatusItem` with its own popover or window (like CodexBar):** full control over opening, closing and position. On macOS 27 the app would have to implement the new Expanded Interface Session itself via `expandedInterfaceDelegate`, where the developer forums report many breakages. v1 doesn't need that control, because the dropdown only opens on click.
- **XcodeGen, Tuist or an Xcode project:** standard Xcode mechanisms and access to Xcode's agent tooling, which however needs Xcode to be open. Costs an extra tool or a project file that can't be created via the CLI.

## Consequences

- **Structure:** Logic and views live in a library (`PacemarkKit`) that knows no provider. Each provider lives in its own library (`PacemarkClaude`) that depends on it, so the compiler keeps provider internals out of the UI and the pace logic ([How does a provider deliver its limits to the UI?](https://github.com/chris-metz/pacemark/issues/13)). The executable target is only the shell with the `MenuBarExtra` scene and the one place that lists the providers. The dropdown is a standalone view with a fixed width; its state lives in the model, not in view state, because `MenuBarExtra` discards view state on close.
- **Menu bar label as one drawn image:** The `MenuBarExtra` label is a single non-template `NSImage` (glyph plus percentage) drawn at draw time, not `Image` plus `Text`. SwiftUI drops every colour and opacity modifier on the label's `Text`, so the red and dimmed percentage would never show. The drawn image passes through untouched and looks like the system label in the real menu bar. Its accessibility text goes on the `NSImage`, because SwiftUI drops `.accessibilityLabel` there too. Verified on macOS 27.0.1 in [Can the menu bar item show a red or dimmed percentage?](https://github.com/chris-metz/pacemark/issues/17).
- **Fallback route:** If `MenuBarExtra` fails on window size or behavior, only the shell is swapped for a custom `NSStatusItem`; the view and the drawn label image stay.
- **Swift settings:** Swift 6 language mode with full data-race checking and `.defaultIsolation(MainActor.self)`. Only the `claude` call runs explicitly in the background.
- **Bundle:** A script builds the `.app` bundle from the SwiftPM build (Info.plist with `LSUIElement`, icon, signature). Launch at login uses `SMAppService.mainApp`, registered only when the user asks.
- **Settings window:** Besides the `MenuBarExtra`, the app has one SwiftUI `Window` scene for its settings: fixed size, a single instance, kept closed at launch with `.defaultLaunchBehavior(.suppressed)`. It opens from "Settings…" in the dropdown footer, with ⌘, and when the user opens the running app again; an `NSApplicationDelegateAdaptor` handles that reopen event, which a menu-bar-only app otherwise ignores. Opening it closes the dropdown and activates the app. The app stays an accessory app throughout, so it never gets a Dock icon or a ⌘-Tab entry: switching the activation policy at runtime is a known source of stuck Dock icons and windows that don't come to the front, which agents can't verify headless. ⌘Q and ⌘, are attached to the Quit and Settings buttons with `.keyboardShortcut`, because a menu-bar-only app has no key equivalents otherwise. If the scene doesn't reliably come to the front, an AppKit `NSWindow` hosting the same view replaces it. Decided in [How do you start and quit the app?](https://github.com/chris-metz/pacemark/issues/14).
- **Self-verification:** Tests use Swift Testing. Snapshot tests render the dropdown and the settings window with sample data and a fixed time via `NSHostingView`, and the menu bar label image under the `vibrantLight` and `vibrantDark` appearances, as PNG in light and dark with an explicit background, and compare them against reference images in the repo. The agent looks at new reference images before accepting them.
- **Remaining gap:** Behavior in the real menu bar (click, position) and whether the settings window comes to the front can't be verified headless. It is tested via model and state, not via UI automation.
- **No third-party dependencies,** not even in tests. Foundation, SwiftUI and our own code cover the child process, JSON and image comparison.
- **macOS 27 as the minimum version:** Older versions would be unverified, especially since the menu bar changed with 27. Anyone still on macOS 26 can't launch the app. The bar can be lowered later.
